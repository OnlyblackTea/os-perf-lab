# Linux 性能排查八股 · Track 设计规格

> 状态：设计稿（未开工）· 对应平台契约见 [`_CONTRACT.md`](./_CONTRACT.md)
> 一句话定位：给「Linux 性能四板斧背得滚瓜烂熟、却从没亲手 `perf record` 过」的后端候选人，
> 用一个**故意跑得很难看的本地服务**，把 top / vmstat / iostat / ss / perf 这些工具从名词变成肌肉记忆，
> 并通过 6 个能确定化的判据，证明他改掉的是**结构性浪费**而不是调参。

## 0. 一页纸摘要

| 项 | 值 |
|---|---|
| track.id | `os-perf-bagu` |
| 骨架仓名 | `os-perf-lab` |

| 与 database-bagu 的关系 | 完全互补、零重叠：seckill-lab 问「慢在 SQL 还是锁」，本 Track 问「慢在 CPU / 内存 / IO / 网络 的哪一层」。seckill-lab 的 Stage 3（锁与超卖）讲的是**数据库行锁**，本 Track 的 Stage 5 讲的是**用户态 futex 锁**——两者是同一个词的两层，规格里刻意在八股地图上标注了这处对照 |
| 预计落地工作量 | 骨架 8~10 → **12~14** 人日 / canonical 测试 6~8 → **11~13** 人日 / 题面与判据 3 → **4.5** 人日 / 分支与 pin 1 → **1.5** 人日（合计 **21 → 29~33 人日**，逐项理由见 §7 的 v1.1 重新估算块；**比 concurrency-lab / mq-lab 更贵**，因为骨架要含**十三个**独立的故意缺陷 + 六个边界守卫 + 六个账本 + 观测脚本，其中三条边界判据要用「确定性序列」构造而不是靠时间） |

**卖点（三条以内）**：

1. **把「不可判的性能」拆成两半**：能确定化的部分（重复编译次数、存活对象数、写入次数、连接建立次数、并发工作数、分位数口径）进 canonical 测试；不能确定化的部分（CPU%、swap、await、futex 延迟）进一份**可复现的实验手册**，要求学员提交实测证据。这是本 Track 最有价值的设计动作，也是它对其他 Track 的可复用产出。
2. **四板斧各有一块「红在对的地方」的骨头**：不是「跑得慢」这种无法验收的红，而是「同一个操作被做了 4000 次 / 缓存无上限 / 每条记录 fsync 一次 / 每个请求新建连接 / 持锁做耗时计算 / 分位数是编的」——六条都能用**计数器**证伪，与宿主内核版本、CPU 型号无关。**v1.1 规模复核后每一关再多两条**：一条打同一处结构浪费的**另一个方向**（二次扫描、驱逐活性、驻留峰值、响应归属、临界区真相、报告量纲），一条打**边界/拒绝路径**（扫描预算、缓存上界、批次上界、池容量、等待队列、并发上限）——边界路径是本 Track 新增判据里最靠近生产事故的那一类，也是「只跑 happy path」的照妖镜。（每条红分属不同不变量的逐条论证见 §1 的 v1.1 块。）
3. **诚实**：本 Track 明确放弃「我能把 CPU 从 90% 降到 30%」这类考核，并把放弃理由写进 §1.5 与 §7。它考核的是**结构性性能回归的发现与消除能力**，不是调参玄学。**v1.1 之后这条立场不变**：扩面全部发生在「计数与结构」这一半，14 条绝对值考点依旧只能进手册。

### 1.0 一句话结论（先说结论，再论证）

这条 Track 的判据可行性**确实是最弱的一条**，但弱的地方可以被精确切出来：
**凡是「相对」或「计数」的考点都能确定化，凡是「绝对值」的考点都不能。**
整个骨架设计因此被一条铁律支配：

> **判据只能读「内核暴露的计数器」或「应用自己暴露的计数器」，绝不能读时间。**
> 唯一的例外是 §1.4 里那条带内建兜底的 A/B 相对改善练习，且它**不进 canonical 测试**。

### 1.1 十八条判据（每 stage 三条不变量）与它们的确定化手段

> 另有 2 条单线程基线与 1 条边界/拒绝路径（见 §1.2 的表与 §4 每张卡的 `expect`）。

| stage | 骨架红在哪（一句话 × 三条） | 判据读什么 | 为什么与内核/CPU 型号无关 | 确定化手段 |
|---|---|---|---|---|
| 1 CPU | ① 在**每行**上重新编译一次正则 ② 排名阶段对**已过滤的**集合又做了一次全量扫描 ③ 候选数已不足 `limit` 时仍把整批扫完（边界短路缺失） | 受保护计数器：`CountingRegex.compileCalls`、`WorkCounter.total`、`WorkCounter.boundaryScans`、`BudgetRegistry.rejected` | 计数是**确定性函数**（输入固定 → 计数固定），不含时间 | 单次固定夹具 + 精确相等/上界；`4n/n` 增长比只作为**辅助**（阈值 8，宽松 4 倍） |
| 2 内存 | ① 元数据缓存**不设上限**，喂 50k 个不同键后存活条目 = 50k ② `evictions` 恒为 0（驱逐这条活性根本不存在） ③ 容量耗尽时既不驱逐也不拒绝，静默越界 | 受保护计数器：`CacheRegistry.liveEntries`、`Evictions`、`AdmissionRegistry.rejected` | 存活条目由我们的 `BoundedMap` 包装器直接数，不靠 GC 时序 | 精确断言：`liveEntries <= capacity`（骨架值 = 键数，跨度 4000 倍）+ 驱逐单调 + 拒绝可数 |
| 3 IO | ① **每条记录**都 `channel.force()` 一次（`forceCalls` = N） ② `RecordSource.readAll()` 把 10 万行一次性读进 `ArrayList`（驻留峰值 = N） ③ 批次无上界：守卫允许把整批一次灌给底层 | 受保护计数器：`forceCalls`、`StreamCursor.materializedPeak`、`PeakBatchSize`、`FsyncPolicyGuard.rejected` | `force` 调用次数就是我们包装器里的一次 Java 方法调用，与磁盘无关；驻留量由游标自己数 | 精确断言：`forceCalls <= ceil(N/B)`、`materializedPeak <= B`、`PeakBatchSize ∈ [B_min, B_max]` |
| 4 网络 | ① **每个业务请求**新建一条 TCP 连接（无 keep-alive、无池） ② **每请求新建线程** ③ 并发复用下响应归属无守护（第 i 次调用可能拿到第 j 次的响应） | 受保护计数器：`connectionsOpened`、`connectionsReused`、`threadsCreated`、`ResponseCorrelator.mismatches` | 与内核无关：连接来自我们注入的 `SocketFactory` 包装器，线程来自我们注入的 `ThreadFactory`，归属由应答里的序号直接核对 | 精确断言：200 次调用 → `connectionsOpened <= 8`；`threadsCreated <= 4`；`mismatches == 0`；`rejected` 可数 |
| 5 锁 | ① 在**一个全局锁**里做耗时计算，锁内工作 = 全部工作 ② 耗时计算期间**始终持有**计数器内部互斥量 ③ 一次成功计数只写进一处口径（另两处不更新） | 受保护计数器：`GuardedWorkConcurrency.peakConcurrent`、`criticalSectionMutexHeldDuringWork`、`ContentionInstrumentation` 的三处口径值 | 计数由包装器的内部计数器累加/递减维护，不读时间；口径对账是整数相等 | 精确断言：`peakConcurrent >= 4`（骨架恒为 1）；工作时互斥持有次数 == 0；三处口径严格相等 |
| 6 容量 | ① 骨架的「P99」是 `mean × 1.2`——**从不读样本**；`p50` 等于 `mean × 1.0` ② `LoadDriver` 只有串行入口，且并发上限形同虚设（要多少给多少） ③ `capacityReport()` 把 P99 当吞吐量打印（量纲串栏） | 受保护断言：分位数必须是**已记录样本中的某个值**；`SampleProjection` 的成员判定；`CapacityReportGuard` 的字段类型表；`GuardedWorkConcurrency.peakConcurrent` | 这是纯结构断言（集合成员关系 + 字段类型 + 整数计数），与时间无关 | 精确断言：`p50 == sorted[samples/2]`、`p99 ∈ samples`、`p50 <= p95 <= p99 <= max`；超上限并发被拒且可数；吞吐字段不含分位数 |

**九条判据的红绿跨度**（骨架值 vs 参考解值，决定了不会被抖动淹没）：

1. `compileCalls`：4000 → **1**
2. `WorkCounter.total`：8000 → **4000**（恰好等于候选集大小）
3. `boundaryScans`（候选数不足 `limit` 时的多余扫描）：2000 → **0**；`BudgetRegistry.rejected`：0 → 恰好 1
4. `liveEntries`：50000 → **<= 1024**
5. `evictions`：0 → **单调增长**；容量耗尽时的 `AdmissionRegistry.rejected`：0 → 恰好 1
6. `forceCalls`：100000 → **<= 782**；`materializedPeak`：100000 → **<= 128**；`PeakBatchSize`：1 → **∈[64,128]**
7. `connectionsOpened`：200 → **<= 8**；`threadsCreated`：200 → **<= 4**；`ResponseCorrelator.mismatches`：>0 → **0**
8. `peakConcurrent`：1 → **>= 4**；工作时互斥持有：>0 → **0**；三处口径：不相等 → **严格相等**
9. `p50`：`mean×1.0`（非样本）→ **`sorted[n/2]`**；`capacityReport` 的吞吐栏：`p99` → **每秒成功次数**

每一条的跨度都在 2 个数量级以上、是一个**布尔翻转**、或是一组**整数严格相等**，因此「跑 3 次取中位数」
在本 Track 里其实只是兜底承诺，判据本身不需要它。

### 1.2 红为什么「红在对的地方」

逐条排除「假红」（编译错 / 脚本为空 / 装配失败 / 基础设施没起来）：

- **先排除编译错**：准入门第一门就是 `bash scripts/build.sh` = `mvn -B -o -DskipTests compile` 必须成功。骨架的**十三个**缺陷全部是**运行期行为缺陷**，不是缺失实现、不是 `TODO`、不是抛异常——每个入口都能被正常调用并返回正确结果（正确性天生绿），红只出现在计数器与结构断言上。这一点和 seckill-lab Stage 2 的形状一致：**功能是通的，缺的是性能性质**。**v1.1 复核后这条对新增的六个 `*Guard` 与六个账本同样成立**（§2.3 的末段有逐条论证）。
- **再排除装配失败**：`@Tag("smoke")` 组在骨架上必须**全绿**（起服务、四个端点各打一次、返回 200 且结果正确）。它是环境体检，是「不是装配问题」的机器证据；它**不进任何 stage 的 canonical 测试组**。
- **再排除「基础设施没起来」**：canonical 测试**不需要 compose**——六个测试组全部在进程内起 `HttpServer`，用 `localhost` 回环 + 随机端口，用进程内夹具代替数据源。compose 只服务于两件事：① 学员跑实验手册里的观测练习；② cgroup 配额演示。准入门里「基础设施可起」这一门靠 `docker compose up` 后 app healthy 满足，但**它不参与任何 stage 的判据**。
- **最后排除「永远红 / 永远绿」**：每个 stage 的 canonical 测试在 `stage-NN-<name>-sol` 上必须绿。这条由 §3 的 `-sol` 分支逐个保证，且 §7 的实施顺序里第 1 步就是先把这条链在一条 stage 上打通再复制。

### 1.3 绿是什么形状（要具体到计数器的数）

以 Stage 1 为例（其余同理，逐张在 §4 的 `expect` 里给成品文案）：

> 跑三遍同一份 4000 行夹具，`CountingRegex.compileCalls()` 的增量恒为 **1**（骨架为 4000），
> `WorkCounter.total()` 的增量恒为 **4000**（骨架为 8000，因为排名阶段又扫了一遍），
> `WorkCounter.boundaryScans()` 恒为 **0**（骨架在"候选不足 limit"的边界上仍扫了 2000 次），
> `BudgetRegistry.rejected("SCAN_BUDGET")` 在超预算那次恰好为 **1**（骨架恒为 0），
> 且 `discover("手机")` 返回的前 20 条 `id` 与参考实现**逐字相同**。

绿是「同一个输出 + 少做了多少工作 + 边界上有人拦」这三件事（输出不变、工作骤降、越限被拒），
不是「快了 X ms」。**v1.1 复核后六个 stage 的绿都按这个形状写**（逐条在 §1.1 的红绿跨度表里）：

| stage | 绿时的可观测形状（全部是不含时间的整数或集合关系） |
|---|---|
| 1 | `compileCalls` 增量恰 1；`WorkCounter.total` 恰 4000；`boundaryScans` 恰 0；超预算时 `rejected("SCAN_BUDGET")` 恰 1 且零副作用；账本与包装器两个口径相等 |
| 2 | `liveEntries ≤ capacity`（50k 个不同键喂完后稳定在 1024 以内）；`evictions` 单调增长；容量耗尽时 `rejected("CACHE_FULL")` 恰 1 且命中语义不变 |
| 3 | `forceCalls ≤ ceil(N/B)`（100000 条 → ≤ 782）；`PeakBatchSize ∈ [64,128]`；`materializedPeak ≤ 128`；越界批次 `rejected("BATCH_OVER_BOUND")` 恰 1 且零写入；回读逐条一致 |
| 4 | `connectionsOpened ≤ 8`（200 次调用）；`threadsCreated ≤ 4`；`mismatches == 0`（含 200 并发）；池容量 4 + 16 并发时 `rejected("POOL_FULL")` 恰 1 且 `connectionsOpened` 始终 ≤ 4 |
| 5 | `peakConcurrent ≥ 4`（8 个工作线程）；耗时计算期间互斥持有次数恰 0；三处口径**严格相等**且等于夹具确定值；`rejected("QUEUE_FULL")` 非零且被拒者零副作用 |
| 6 | `p50` 等于样本排序后的第 n/2 个值（±1 索引口径）；`p50 ≤ p95 ≤ p99 ≤ max` 且都是样本成员；`rejected("FIELD_MISMATCH")` 与 `rejected("CONCURRENCY_OVER_CAP")` 各恰 1；错栏报告零外发 |

> **一张表说清 A/B 两类的边界**（v1.1 复核后逐 stage 固定）：
> **A 类 = 每 stage 6 条用例**（3 条红 —— 即上表的 18 条不变量 / 2 条单线程基线 / 1 条边界路径），六个 stage 共 **36 条**；
> **B 类 = §1.5 那 14 条 + §1.4 末尾那条带兜底的相对改善实验**，全部只进实验手册与答辩，
> **不参与 AcceptanceDecision**。这两类的划分在本轮**一条都没有变动**。

### 1.4 抖动指标的处理（本文档最要紧的工程细节）

本 Track 里可能抖的东西共有六类，逐个给处置：

| 抖来源 | 会不会进判据 | 处置 |
|---|---|---|
| **CPU% / load / QPS / 延迟 ms** | ❌ 绝不 | 只出现在实验手册里，作为**学员提交的证据**，由人读、不进 AcceptanceDecision |
| **GC 停顿 / 堆占用字节数** | ❌ 不进判据 | Stage 2 判「存活条目数」而不是「堆字节数」。理由：字节数受 JVM 版本、TLAB、压缩指针影响；条目数是我们自己数的 |
| **磁盘吞吐 / `await` / `%util`** | ❌ 不进判据 | Stage 3 判「`force()` 调用次数」与「批次上界」。理由：`await` 依赖底层块设备（SSD/NVMe/网络盘差 100 倍） |
| **时间窗内的并发度** | ❌ 不进判据 | Stage 5 判「同时在耗时计算中的线程数峰值」而不是「墙钟加速比」。理由：墙钟依赖宿主核数 |
| **JIT 预热** | ✅ 可以消除 | 所有计数器都是「增量」而非「总量」，且每组测试固定 `-XX:-TieredCompilation` 无关的预热调用（每组开头跑 3 次 warmup，**不在这 3 次里读数**）。计数与 JIT 无关，预热只是为了让「如果将来有人加了时间断言」也不抖 |
| **文件系统语义差异**（tmpfs 上 `force()` 是无操作） | ✅ 可以消除 | Stage 3 计数器数的是**我们包装器里的方法调用**，不是文件系统真的落盘没落盘；夹具目录用 `@TempDir`（可能在 tmpfs 上），因此断言必须与「真的写下去没有」解耦——这一点在 tickets 里明写成设计约束 |
| **测试执行顺序 / 并行** | ✅ 可以消除 | 受保护计数器在 `@BeforeEach` 里 `reset()`；Surefire 配 `forkCount=1`、`reuseForks=true`、`parallel=none`（写进 `pom.xml`，属判定面） |

**唯一的例外**（带内建兜底，仍然不进 canonical 测试）：Stage 6 的实验手册给一条**相对改善**判据——

> 同一台机器、同一个 cgroup 配额、同一份夹具，连跑 3 次取中位数：
> 修好「持锁做耗时计算」之后，Stage 5 批次操作的 P99 **相对**下降 ≥ 30%。
> 兜底条款：若基线 P99 < 5ms（说明宿主足够快、锁竞争不显著），该条自动判「不适用」而不是判红。

写这条的目的是给学员一个**能自己看见改善**的正反馈；把它排除在 canonical 之外，是因为它同时依赖宿主核数与调度器——**抖动指标不能作为唯一判据**，而在这条 Track 里它连判据都不是。

### 1.5 不可判定或需要妥协的考点（诚实列出，不藏）

以下考点**只能**做成实验手册 / 可观测练习，进不了 canonical 测试。每一条给出「为什么」：

| # | 考点 | 为什么不能进 canonical | 降级后的形态 |
|---|---|---|---|
| 1 | CPU 使用率百分比、`%sys`/`%usr` 比例 | 绝对值，依赖核数与宿主负载；同一份代码在 2 核笔记本与 32 核服务器上差一个数量级 | 手册：固定 cgroup `--cpus=2`，跑同一份夹具，`top -b -n1` 记录 `%usr` 前后对照 |
| 2 | 平均负载 / 运行队列长度 | 同为绝对值，且受同机其他进程影响（学员机器不是隔离环境） | 手册：`vmstat 1 10` 的 `r` 列对照 |
| 3 | 火焰图形态与热点占比 | 火焰图是**采样**产物，占比每次不同；且需要 `perf` + FlameGraph 工具链（离线不一定有） | 手册：`perf record` + `perf report` 文本输出，剪一段栈贴进答辩；占比只作定性 |
| 4 | swap 使用量、换页速率（`si`/`so`） | 需要宿主真的开 swap 且内核版本影响回收行为；很多开发机 `swap=0` | 手册：`free -m` + `/proc/vmstat` 的 `pswpin/pswpout` 对照；无 swap 时判「不适用」 |
| 5 | OOM killer 是否触发、杀了谁 | 依赖 cgroup v1/v2 差异、`oom_score_adj`、内核版本；且触发一次可能把学员自己的 IDE 杀掉 | 手册（**可选、显式警告**）：`docker run --memory=256m --memory-swap=256m` 里跑一个 512MB 分配的演示程序，读 `dmesg`/容器退出码 137。**明确标注「可能影响同机其他进程，建议在专用 VM 里做」** |
| 6 | 页缓存命中率、`free` 的 `buff/cache` 语义 | 依赖宿主整体内存压力，不可重现 | 手册：`vmtouch`/手工 `dd` 后对 `cached` 列的前后对照，**只解释语义** |
| 7 | `iostat` 的 `await` / `%util` / 直接 IO vs 缓冲 IO 的倍率 | 依赖块设备（SSD/NVMe/网络盘/virtio 差 10~100 倍） | 手册：同一块盘上 `dd oflag=direct` vs `oflag=dsync` vs 无 flag 的三向对照，看**趋势**不看数字 |
| 8 | `fsync` 的延迟极值（p99.9 常见 10~100ms 尖刺） | 依赖盘与页缓存状态；这就是「抖动指标」的教科书案例 | 手册：`fio --fsync=1` vs `fio --fsync=32` 的 IOPS 对照；**只给趋势** |
| 9 | TIME_WAIT 堆积、临时端口耗尽（`BindException`） | 是否需要端口耗尽取决于 `net.ipv4.ip_local_port_range`，且要跑几千次连接才可能触发 | 手册：`ss -s` / `ss -tan state time-wait` 计数对照 + 端口范围计算题（**计算是确定的，现象不是**） |
| 10 | 上下文切换次数（`cs` 列）绝对值 | 绝对值受核数、同机负载影响；`/proc/self/status` 的 voluntary 计数可以用，但先修哪个由人判断 | 手册：`vmstat 1` 的 `cs` 列 + `/proc/self/status` 的 `voluntary_ctxt_switches` 对照 |
| 11 | `perf trace` 的 syscall 延迟分布 | 需要 `perf` 与内核 tracepoint 权限；延迟是抖的 | 手册：`perf trace -s` 的**调用次数**表（次数是确定的，延迟不是） |
| 12 | `perf lock` 的等待时间/次数 | `perf lock` 依赖 `CONFIG_LOCKDEP`/锁事件与 root；次数能读、时间不能 | 手册：`perf lock record/report`；**只讲「谁在等锁」**，等待时长不论断 |
| 13 | 锁竞争的墙钟加速比 | 依赖核数（单核机器上并发优化**没有收益**） | 手册：`taskset -c 0-3` 固定 4 核后做 A/B；单核机器自动判「不适用」 |
| 14 | QPS、TP99 的**绝对值**、容量评估结论（「这台机器能扛多少」） | 平台禁止「特定硬件型号」依赖；绝对值换台机器就变 | 手册：给出**容量评估方法论**（小流量测单请求成本 → 按目标 QPS 反推实例数 → 留 30% 余量），要求学员交一份**带假设与误差范围**的结论；评分看方法论是否自洽，不看数字对不对 |

**这张表就是本 Track 的价值所在**：14 条降级项没有一条被隐藏，全部有明确的「为什么」和「换成什么」。

> **v1.1 规模复核对本节的唯一改动**（本轮只加了这一句，14 条一条未动）：扩面新增的判据
> （§1 的 v1.1 块里那 12 条新不变量）**全部**是「计数器 / 结构断言 / 集合成员关系」——
> 扫描次数、存活条目数、驱逐次数、驻留峰值、批次上界、建连与建线程次数、响应序号归属、
> 并发峰值、拒绝次数、分位数是否可取到该样本值、报告字段量纲。**没有一条是从上表里"升级"上来的**：
> 这批新量的确定性是刻意挑出来的（输入固定 → 计数固定；集合成员关系与时间无关），
> 而不是把时间阈值或 A/B 幅度的对比偷偷放进断言。实施时若有人把 `rejected == 1` 改写成
> 「拒绝时延 < 1ms」、或把 `PeakBatchSize` 改写成「单批耗时 < 2ms」，那就越过了本节的边界，
> 属于**废稿级**的改法——上表每一条的「为什么不能进 canonical」对新增判据同样有效。

### 1.6 「一半考点只能做手册，那还值不值得做成 Track？」

**结论：值得，但必须收窄——收窄的依据正好是 §1.1 那张表。**

判断理由分三层：

1. **判据硬的那一半足够撑起一条 Track。** 六个 stage 里有 **5 个**（CPU / 内存 / IO / 网络 / 锁）的核心判据是**计数器断言**，红绿跨度 2 个数量级以上，跨平台稳定；第 6 个（容量评估）至少有一条**纯结构断言**（分位数必须是样本）撑着，不是空的。也就是说这条 Track **不靠**「绝对值」过判别性门——它可以独立通过 `paper validate-track`。**v1.1 规模复核后这条结论只变强不变弱**：A 类判据从 6 条计数器扩到 18 条（每 stage 3 条不变量），而上面那 14 条 B 类考点**一条未动**——扩面全部发生在"能确定化的那一半"里面，没有把任何一条绝对值考点挪进判据（逐条见 §1 的 v1.1 块末段）。
2. **降级项不是「没做的部分」，而是「产品的一部分」。** 性能排查这门手艺的面试形态本来就是「你说说 drop_caches 之后 free 的 cached 列为什么变了」；把这些做成**要求提交实测输出的实验手册**，比强行造一个会 flaky 的断言更接近真实面试，也更接近 seckill-lab「你面试时要能讲出自己的思路」的立场。canonical 测试负责**防作弊的那一半**（结构性浪费必须被消除），手册负责**讲得出来的那一半**。
3. **收窄后的版本（本规格采用的就是它）**：6 个 stage 全部保留，但每个 stage 的验收被明确定义成两件事——
   - **A 类（进 canonical，硬）**：**v1.1 之后每个 stage 是三条**计数器/结构断言，各自打一条不同的不变量
     （「结构性问题是否消除」的**三个不同侧面**：浪费的次数、边界的值、上限的守卫），外加 2 条单线程基线与 1 条边界/拒绝路径；
   - **B 类（进手册，软）**：一到三条观测练习，要求提交原始命令输出与自己的解读，**不参与 AcceptanceDecision**。
   §4 每张 ticket 的 `expect` 与 `submission.template.require` 都按这两类分开写（`expect` 里每条用例都标了「红/基线/边界」
   与它验的不变量），学员一眼能看出「哪部分是过关硬门、哪部分是要在面试里讲出来的」。

   > **A 类扩容与 B 类无关**：本轮 A 类从 1 条扩到 3 条，靠的是把同一处结构浪费的另外两个方向
   > 与它的边界路径提成独立不变量，**不是**把手册里的某一项改成断言。B 类练习的条数与写法一字未改
   > （每 stage 一到三条，全部要求提交原始输出），也没有任何一条被移出「不进 AcceptanceDecision」的范畴。

**同时诚实标注三个「如果……就不该做」的触发条件**（写进 §7 风险表）：

- 若**离线**跑不通 `mvn -o test`（依赖没预热），本 Track 直接作废——它比 seckill-lab 更依赖大包（JUnit、Surefire、Compiler 插件）。这是**头号开工前提**。
- 若目标学员群体的机器**普遍没有 `perf`**（很多发行版把它拆成 `linux-tools-$(uname -r)`），本 Track 的 **B 类价值**会掉一半（但 A 类不受影响，Track 仍成立）；因此 §6 的 `requires` 必须显式声明 `perf` 可选，且骨架**绝不**依赖它。
- 若上游 `ticket.schema.json` 未来加了 `kind: lab` 之类的字段，本 Track 的 B 类练习应迁进去变成一等公民；现在只能塞在 `submission.template.require` 里，是**规格向 schema 妥协**的地方，已在 §7 记账。

### 2.2 分层与约定

- **业务层只有一层**（`com.devteam.osperf`），不搞 Controller/Service/Mapper 三层：本 Track 的考点是**系统层行为**，多一层分层只会让「谁该持有锁」这种问题变得含混。真正负责「不许改」的是 `http/` 包（Servlet 只做参数解析与 JSON 序列化，**不含任何循环**）。
- **所有观测点走 `fixture/` 里的包装器**，业务代码通过**构造器注入**拿到它们。约定写在 `docs/架构与约定.md`：
  > 任何「贵操作」都不许直接调 JDK，必须经过 `fixture` 提供的 facade——这样判定面才能**数得清你到底做了几次**。
  这条约定是本 Track 能成立的技术前提：它把「性能性质」变成了**可数的对象身份**。
- **facade 是真委托**，不是假替身：`CountingRegex.compile(s)` 真的返回 `Pattern.compile(s)`；`CountingChannel.force()` 真的调 `channel.force()`。所以夹具写下去的数据是真数据，任何「靠假实现骗计数」的路径都会同时打死正确性断言。
- **分类账：哪些文件是「可判的改动面」**（v1.1 复核新增的这条纪律，照 `concurrency-lab` v1.3 对 `ObjectHeaderProbe` 的处理）。
  改动面文件分三档，**只有前两档能拿来满足 `scope.files_to_change ≥ 3` 与三类角色的下限**：
  ① **核心状态/算法载体**（`ProfileService` / `CatalogCache` / `BatchRecordSink` / `RecordSource` / `UpstreamClient` / `GuardedCounter` / `LatencyRecorder` / `LoadDriver`）；
  ② **边界与编排载体**（六个 `*Guard`）——它们是**独立的可判文件**，每条边界判据都真的钉在它们身上；
  ③ **观测工具**（`ContentionInstrumentation` / `ResponseCorrelator`）——它们**只把量暴露出来**，判据打在业务文件与 `fixture/` 包装器上，
  因此规格明确：**这两个文件不承担三类角色、也绝不拿来充数**（它们在 Stage 4 / Stage 5 的改动面里出现，但那两个 stage 各自另有三档①②的文件满足下限）。
  观测包装器本身（`fixture/` 下 13 个类）**全在判定面内**，不进任何 `scope.files_to_change`——它们是「判据」，不是「待改的代码」。
  这条纪律的作用是防一种具体的注水：**补一个只打印的观测工具，把它算成"第三个文件"**。
- **不许改的脚手架**：`http/`、`json/`、`Main.java` 的 CLI 参数解析部分（参数名固定）。理由：判据要能稳定地驱动同一批入口，参数一改判据就找不到入口了。
- **v1.1 的「每 stage 三个文件」固定形状**（照 `concurrency-lab` 定稿后的写法，让六张工单可以并排比对）：
  每张工单的 `scope.files_to_change` 恒为三个业务文件，角色分工固定为
  **① 核心状态与算法 + ② 计数/观测账本（`*Ledger` 或 `*Instrumentation`） + ③ 调用编排与异常·边界路径（`*Guard`）**。
  其中 ①③ 的证据来自**判定面**的包装器（`fixture/CountingRegex` / `CacheRegistry` / `CountingChannel` /
  `CountingSocketFactory` / `CountingThreadFactory` / `GuardedWorkConcurrency` / `SampleProjection`），
  因为这些判据读的是"你经过 facade 做了几次贵操作"；② 自己也是可断言的业务账本（"这一次请求/这一个批次里，
  我统计出来的量与真正发生的量一致吗"），它同时是**统计口径**这一路扩面的落点，并被 §4 每张卡的 `expect` 直接断言。
  一个例外要记住：**账本不许用来替代判定面的包装器**——如果账本与包装器的读数不一致，判据按包装器判（它是受保护的），
  账本那一路会连带红；也就是说"自己写个计数器把数字凑好看"这条路走不通。
  这条形状同时解决了两件事：`files_to_change ≥ 3` 不是靠补一个只打印的工具凑出来的，
  而且每一关都真的要多协调一处**共享的统计口径**——这正是 `_SCALE.md` §2 说的「同 stage 扩面」。

| D3 | `CatalogCache.java` | `put()` 只用 `HashMap`，**从不驱逐**；`capacity()` 字段存在但无人读；`evictions` 恒为 0 | 2 |
| D4 | `CacheLoadGuard.java` ★v1.1 | 容量耗尽时既不驱逐也不拒绝：`admit()` 永远返回「已准入」，静默越界（拒绝语义不存在） | 2 |
| D5 | `BatchRecordSink.java` | 逐条 `parse → channel.write → channel.force()`；每批只放 1 条 | 3 |
| D6 | `fixture/RecordSource.java` | 只有 `readAll()`：把 10 万行一次性读进 `ArrayList`，**没有流式游标** | 3 |
| D7 | `FsyncPolicyGuard.java` ★v1.1 | 批次上界是个**恒真判断**（`batchSize <= Integer.MAX_VALUE`）：既允许一次灌 10 万条，也不记录被拒的批次 | 3 |
| D8 | `UpstreamClient.java` | 每个 `quote()` 都 `SocketFactory.createSocket()` 新建连接，读完不池化不 keep-alive；`serve()` 每请求 `new Thread()` | 4 |
| D9 | `ConnectionBudgetGuard.java` ★v1.1 | 池容量上限形同虚设：请求多少连接就给多少，耗尽路径不存在（`rejected` 恒为 0） | 4 |
| D10 | `ResponseCorrelator.java` ★v1.1 | 用一个「当前在飞请求」的普通字段做归属，**串行下正确、并发下串号**（响应可能落到别的调用方手里） | 4 |
| D11 | `GuardedCounter.java` + `GuardedSink`（同文件内静态类） | `applyBatch()` 把 `WorkloadServlet` 传进来的**整个批次**放进 `synchronized` 块里做耗时计算；且一次成功计数只写进播报口径，另两处不更新 | 5 |
| D12 | `LockAdmissionGuard.java` ★v1.1 | 等待队列**无上界**：锁上排队的线程数不限、也不拒绝（队列耗尽路径不存在） | 5 |
| D13 | `LatencyRecorder.java` + `LoadDriver.java` + `CapacityReportGuard.java` ★v1.1 | `percentile(p)` 返回 `mean * factor[p]`（**从不读样本**）；`LoadDriver` 只有 `runSerial()` 且并发上限不检查；`capacityReport()` 把 p99 当吞吐打印，`CapacityReportGuard` 对该错栏**不报错** | 6 |

**D1..D13 刻意正交**：它们分别落在不同的类、不同的方法、不同的调用链上，没有一条的修复依赖另一条
（唯一需要点名的一处耦合是 D3/D4：`CatalogCache` 是缓存本体，`CacheLoadGuard` 是它容量耗尽时的准入/拒绝路径，
两者改的是同一处语义的**两个不同侧面**——缓存本体管「存多少」，守卫管「存不下时怎么办」，
判据也分别打在 `liveEntries`/`Evictions` 与 `AdmissionRegistry.admitted()/rejected()` 上，互不覆盖）。
这条性质在 §3 里被用来保证「链式分支只加不删」成立，在 §4 每张 ticket 的 `expect` 里被明写为
「本 stage 的改动不会让前序 stage 的判据变红」。

**D1/D2、D3/D4、D5/D6/D7、D8/D9/D10、D11/D12、D13 的「单线程也都对」论证**（`_SCALE.md` §1.1 第 1 条）：
上表 13 条缺陷的骨架实现**都走完了正常路径并返回正确结果**，只有 D10（响应归属）与 D11 的第二半
（三处口径不齐）是**确定性序列复现的逻辑缺陷**（单线程可见，已点名类别）；其余 11 条全是
**超限或并发才暴露**的形态（无上限缓存、逐条 fsync、每请求建连、持锁做耗时计算、预算/容量/队列不检查）。
两类都不进 `stage00` 冒烟、都能通过全部单线程基线——冒烟在骨架上是绿的（§2.5）。

### 2.4 基础设施

```yaml
# docker/docker-compose.yml（草纲）
services:
  app:
    build: { context: .., dockerfile: docker/app.Dockerfile }   # eclipse-temurin:17-jdk（digest pin）
    container_name: osperf_app
    command: ["java","-XX:+UseSerialGC","-jar","/opt/osperf/os-perf-lab.jar","serve","--port","8080"]
    ports: ["18081:8080"]                 # 刻意避开 8080/18080 等常用端口
    cpus: "2.0"                           # ★固定配额：实验手册里 CPU% 对照的前提
    mem_limit: 1g
    deploy: { resources: { limits: { cpus: "2.0", memory: 1024M } } }   # 兼容 swarm 语法
    healthcheck:
      test: ["CMD","sh","-c","curl -fsS http://127.0.0.1:8080/health || exit 1"]
      interval: 5s

  pinger:

    entrypoint: ["/bin/sh","/pinger.sh"]

```

- **端口约定**：app 宿主 `18081`，进程内 canonical 测试用**随机空闲端口**（`new ServerSocket(0)` 取端口后关闭再起服务），避免与学员本机任何服务打架。
- **healthcheck 的设计理由**（照 seckill-lab 那条「健康检查必须代表**可连接**，不是进程还在」）：`/health` 端点只有在四个业务端点都完成一次自检（缓存已装载、`fixture` 目录可写、上游回环 server 可连）后才返回 200，否则 503。这样 `depends_on: service_healthy` 才有意义。
- **种子数据量级**：`Fixtures.java` 里固定三档——`small` 4,000 行、`large` 100,000 行、`keys` 50,000 个不同键，全部由固定 seed 的 `java.util.Random` 生成，**不开线程、不读外部文件**。这三档正是 §1.1 里那些计数器数值的来源。
- **资源配额为什么必须在 compose 里**：判据不读时间，但**实验手册 A/B 对照必须固定配额**，否则「修好之后 CPU 从 90% 到 40%」这种观察根本不可比。配额写在 compose 与手册里，是 B 类的可复现前提。

### 2.5 冒烟测试

`src/test/java/com/devteam/osperf/smoke/SmokeTest.java`，`@Tag("smoke")`：

- 进程内起 `LabHttpServer`（随机端口），四个端点各打一次，断言 200 + 结果非空 + `TinyJson` 能解析；
- 断言 `preflight.sh` 的关键输出能被解析（`perf` 存在与否**只记录不失败**）；
- **必须在骨架上全绿**，且**不出现在任何 stage 的 `grader.correctness.test_group` 里**。理由与 seckill-lab 一致：它是环境体检，不是红→绿的考核；把它塞进 stage 会让「骨架红」这条门失效。
- **v1.1 复核后的新增约束（`_SCALE.md` §1.1 第 1 条）**：冒烟必须在**六个 `*Guard` 与两个观测件全部就位**的情况下仍然全绿。
  它们每一个的单线程正常路径都要走完：`QueryBudgetGuard` 在不超预算时放行、`CacheLoadGuard` 在容量之内准入、
  `FsyncPolicyGuard` 在批次合法时放行、`ConnectionBudgetGuard` 在池容量内发放、`LockAdmissionGuard` 在队列未满时入队、
  `CapacityReportGuard` 对合法报告不报错。**任何一条新增缺陷让冒烟变红，就说明它不是"边界/并发语义缺失"而是"功能没写完"，
  必须退回重做**（这正是 `concurrency-lab` Stage 1 扩编第一版踩过、并已回写 `_SCALE.md` §1.1 的那个坑）。
  冒烟里额外加一条**可判性自检**：六个守卫在骨架上各被调用一次，断言"放行/准入"路径的返回值正确，
  但**不**断言它们的拒绝计数（那是 canonical 的事）——这样冒烟证明的是"骨架功能是通的"。

### 2.6 防剧透边界

- 六个 `stage-NN-<slug>` 分支里**只有骨架 + 截至本阶段的测试**，没有任何实现；答案只在 `<slug>-sol` 上。
- `solutions` = 全阶段参考解，**不作任何 stage 的 base/head**。
- `src/main/java/com/devteam/osperf/` 里的**十六个改动面文件在骨架里都是「能跑但难看」**，不是空实现——但它们的 Javadoc 只描述**契约**（例如 `CatalogCache.capacity()` 的注释写「本缓存承诺不保留超过 capacity 个条目」、`QueryBudgetGuard.budget()` 的注释写「本守卫承诺每请求扫描次数不超过 budget」，`CacheLoadGuard.admit()` 写「容量耗尽时必须由本方法给出确定结论，不得静默越界」），**不写怎么实现**。这条是 D2（防剧透）在骨架里的落点：契约必须写清（否则判据不可预期），实现必须不写。**v1.1 新增的六个 `*Guard` 同样如此**：它们的 Javadoc 只写清「超限时该返回什么、该记什么数」，绝不写「在哪里检查、怎么拒绝」。
- `TASKS/*-manual.md`（实验手册）是**公开的**，里面只有「怎么观测」和「看到什么算正常」，**不含修复方向**。手工审一遍：手册里不许出现「把 X 提到循环外」这种句子。

> `progression.prerequisites` 仍是六节点线性链（`[]` → `os-stage-01` → … → `os-stage-05`），
> 分支名、`-sol` 的切出点、`git log --oneline` 的「一级多一个测试文件」这条自检**全部不变**；
> 每级新增的骨架文件（该 stage 的那个 `*Guard` 及其观测包装器）跟着**同一级**的 base 与 `-sol` 一起走，
> 不引入任何跨级依赖。若当初选择合并（例如把 01 与 02 并成「内存与 CPU 的局部性」），就必须重算
> 整套依赖与六条分支，并把 §1.2「红得越窄越能证明判据钉在业务缺陷上」这条论证一起打掉——
> 这也是本轮一个都不合并的第三条理由（前两条见 §1 的 v1.1 块）。

**依赖形状**：一条**链**（`1→2→3→4→5→6`），没有 DAG 分叉。这不是偷懒，而是三个理由：

1. **教学顺序就是排查顺序**。真实排查是「先看 CPU → 再看内存 → 再看 IO → 再看网络 → 最后怀疑锁」，把它做成 DAG 分叉会让「下一步查什么」这件教学上最重要的判断消失。
2. **B 类实验手册有一个共享前置**：`scripts/preflight.sh` 要先把 `perf` / cgroup / swap 的可用性摸清，后面的手册都建立在它之上。分叉会让这份前置要点三遍。
3. **链式分支的合并语义最简单**（`_CONTRACT.md` §5）：学员的 `dev` 每次只做一次「只加不删」的 merge，不会遇到任何冲突。6 条链 × 6 个互相正交的缺陷，是这个契约能成立的最简形态。

### 3.2 只加不删 + 正交性论证

链式分支的硬要求是「`stage-NN` = `stage-(NN-1)` + 本阶段测试」，推论的硬要求是**本阶段的修复不能让前序阶段的测试变红**。本 Track 靠在骨架里把缺陷**放在不同的类/方法**上满足它（v1.1 后是 13 条，逐条对应见 §2.3）：

| 修复 | 落在哪个方法 | 会不会动到别的 stage 的观测点 |
|---|---|---|
| D1 修 CPU 热点 | `ProfileService.discover()` | 只影响 `CountingRegex.compileCalls` / `WorkCounter.total` / `WorkCounter.boundaryScans`；与缓存、IO、连接、锁、分位数全不相干 |
| D2 修扫描预算边界 | `QueryBudgetGuard.check()` | 只影响 `BudgetRegistry` 的拒绝计数；它不读夹具、不碰 channel/socket/锁 |
| D3 修缓存上界 | `CatalogCache.put()/get()` | 只影响 `CacheRegistry.liveEntries` / `Evictions`；Stage 1 的测试不读缓存计数 |
| D4 修容量耗尽的准入/拒绝 | `CacheLoadGuard.admit()` | 只影响 `AdmissionRegistry`（缓存那一桶）；它不碰 `CatalogCache` 的内部容器，判据分别打在两个不同的读数上 |
| D5 修 fsync 批量 | `BatchRecordSink.commit()` | 只影响 `CountingChannel.forceCalls`；它自己拥有那条 channel，不与别人共享 |
| D6 修流式读取 | `RecordSource.stream()` | 只影响 `StreamCursor.materializedPeak`；`readAll()` 的现有调用方语义不变，`forceCalls` 不被它影响 |
| D7 修批次上界守卫 | `FsyncPolicyGuard.check()` | 只影响 `PeakBatchSize` 的上界方向与 `AdmissionRegistry`（IO 桶）；它不调 `CountingChannel.force()` |
| D8 修连接复用 | `UpstreamClient.quote()/serve()` | 只影响 `CountingSocketFactory` / `CountingThreadFactory`；用的是自己的回环 server |
| D9 修池容量与耗尽 | `ConnectionBudgetGuard.acquire()` | 只影响 `AdmissionRegistry`（网络桶）的拒绝计数与池容量读数；它与连接复用是两个方向的读数 |
| D10 修响应归属 | `ResponseCorrelator.bind()/match()` | 只影响 `mismatches`；它不计数连接、不计数线程 |
| D11 修锁粒度 | `GuardedCounter.applyBatch()` | 只影响 `GuardedWorkConcurrency`（并发峰值与互斥持有）与 `ContentionInstrumentation` 的三处口径；它不调 `CountingRegex`，也不碰 channel/socket |
| D12 修等待队列上界 | `LockAdmissionGuard.acquire()` | 只影响 `AdmissionRegistry`（锁桶）与队列长度读数；它不持有计数的互斥量 |
| D13 修分位数口径与报告字段 | `LatencyRecorder.percentile()` / `LoadDriver.runConcurrent()` / `CapacityReportGuard.emit()` | 只影响 `SampleProjection` 的成员判定、并发峰值读数与报告字段类型表；它不驱动任何真实负载 |

**验证方式（写进准入门）**：把**全部 13 个修复**叠上（= `solutions` 分支），跑 `mvn -o test -Dgroups=stage01,stage02,stage03,stage04,stage05,stage06`，必须**六组全绿**。这条「叠加绿」门是链式契约在判据层面的机器证据；只有 `-sol` 单向绿（本阶段绿）而叠加红，说明某个修复越界了。

## 4. 逐张 ticket 卡

> 八个 concern 逐张写全，字段口径与 `seckill-lab/stages/stage-02-order-transaction/ticket.yaml` 对齐。
> 每张卡后面附「泄漏自查」，说明为什么题面没给答案、hints 停在哪一层，以及末尾的**规模自查**。
>
> **规模（按 [`_SCALE.md`](./_SCALE.md) 的下限，v1.1 复核后逐张重写）**：`scope.files_to_change`
> **3 个文件**且覆盖三类角色——① 核心状态/算法（含 `fixture/` 里的计数包装器所观测的那处结构）
> ② 计数/观测包装器（把"调用了多少次"变成可断言的量）③ 调用编排或异常·边界路径（`*Guard`）；
> canonical **6 条 = 红 3（分属**三个不同不变量**）+ 单线程基线 2 + 边界/拒绝 1**，考点族 ≥2 个，

    这次的嫌疑对象是 `CatalogCache`——一个商品元数据的本地缓存。它被加的初衷非常正当：
    元数据变化很少，每次搜索都去查一遍太浪费。但它上线两周之后就成了整个服务的上限。

    ## 问题表现

    `CatalogCache` 的契约里写着一个容量上限 `capacity()`，实现里也确实存了这个字段，
    但**没有任何一行代码读过它**。于是缓存的存活条目数等于「服务启动至今被查询过的不同
    商品的个数」——这是一个只增不减的量。压测环境之所以没暴露它，是因为压测只用了固定的
    几百个商品 id；真实流量里长尾商品会源源不断出现。

    内存问题在这里的形态很典型：**它不会在你测试的时候表现出来，它只会在你上线之后按时
    出现**。所以这道题的判据不是「RSS 有没有降下来」（那取决于你的机器有多少内存、
    swap 开没开、JVM 什么时候 GC），而是「这个数据结构有没有遵守它自己声明的上限」。

    ## 你需要完成的修改

    本题需要修改**三个**文件，它们分别承担三个角色：

    - `src/main/java/com/devteam/osperf/CatalogCache.java`（**核心状态与算法**）：`put()`/`get()` 现在只往
      `HashMap` 里放、从不驱逐，`capacity()` 字段形同虚设。要让缓存**在任何访问序列下**
      都不保留超过 `capacity()` 个条目，同时保持「命中时返回正确值、未命中时决定权交给
      调用方」的现有语义。
    - `src/main/java/com/devteam/osperf/CacheAdmissionLedger.java`（**计数/观测账本**）：它记三笔账——
      放进去几个、因为满了被赶出去几个、因为**放不下而"越界尝试"**了几个。约定是它必须与判定面
      `fixture/CacheRegistry` 的读数**一致**（包装器受保护、不许改；判据以它为准，账本对不上则连带红）。
      现在这本账只记了第一笔，第二笔恒为 0，第三笔根本不记。
    - `src/main/java/com/devteam/osperf/CacheLoadGuard.java`（**调用编排与边界路径**）：它是容量耗尽时的
      **准入判定**入口，契约是「容量之内准入；容量已满时必须给出确定的结论，且该结论要被记下来」。
      现在的实现永远返回"已准入"——它既不驱逐也不拒绝，于是缓存静默越界。

    有一条边界约束必须守住：驱逐与拒绝都不能改变**命中语义**——同一个键在被驱逐之前重复查询
    必须命中，且返回的是同一个值；被拒绝的那一次**不得对已有的条目产生任何副作用**

    单人调试时完全看不出问题——它的代价只有在**频率**上来之后才出现。

    ## 问题表现

    两件事同时发生，而且它们是同一件事的两面。第一，**连接建立次数等于业务请求次数**：
    调用 200 次就有 200 次三次握手，也就有 200 次连接关闭。第二，每次 `serve()` 都新建
    一个线程来处理，于是**线程创建次数也等于请求次数**。

    这两件事都指向同一类开销：**每次交互都在重建一个本可以被复用的东西**。三次握手要花
    掉一个 RTT 与服务端的连接表项；连接关闭之后主动关闭方会进入 `TIME_WAIT` 并占用一个
    临时端口。端口是有限资源（范围由 `net.ipv4.ip_local_port_range` 决定），当
    建连速率 × 2×MSL 超过可用端口数时，就必然出现「没有端口可分配」。而线程创建虽然比
    建连便宜，但它带来的是要由内核调度器付出的上下文切换成本。

      现在的实现用**一个"当前在飞请求"的普通字段**记归属：串行下完全正确，一旦有多个请求同时在飞，
      后到的请求会把前一个的归属覆盖掉，于是响应可能被交给错的调用方，而账本一笔都不记。

    不要绕开它们（比如自己起一个 `Executors`，或用 `HttpClient` 另建一条通道），
    否则你的复用不会被看见——真实的复用也不该绕开这两个注入点。

    必须保证每条请求的响应仍然回到发起它的调用方手里；`UpstreamClient` 的现有契约是

## Stage 1 · CPU 热点与火焰图 ⬜

**亲手场景**：搜索接口把 8 核打满 → 你用 `perf record/perf report` 找到栈顶那个重复的准备动作，把它移出循环。

| 考点 | 一句话原理 | 面试题 |
|------|-----------|--------|
| `%usr` vs `%sys` | 用户态时间是自己代码烧的，系统态高说明在与内核频繁交互（syscall、缺页、锁） | CPU 使用率高，怎么判断是业务代码还是内核在忙？ |
| load average | 可运行 + 不可中断（D 状态）任务数的 1/5/15 分钟指数平均，**包含等 IO 的进程** | load 高但 CPU 不高，可能是什么原因？ |
| perf 采样与火焰图 | 按固定频率采栈、把同一栈折叠计数，宽度代表占比、由下往上是从调用者到被调用者 | 火焰图怎么读？看到一片平地说明什么？ |
| 循环不变量外提 | 不随迭代变量变化的计算应该只做一次；它与「缓存结果」不同，省的是重复工作而非重复查询 | 优化循环时你第一步看什么？ |
| 复杂度与常数 | O(n²) 在 n=1000 时可能比 O(n log n) 更快，但规模一涨必输；判据要能**计数**而不是计时 | 为什么不能只看一次压测的耗时下结论？ |
| 基准测试的确定性 | 同一台机器上跑两次不同结果 = 测量方法有问题；要么固定输入计数，要么做多轮统计 | 你怎么保证你的优化结论是可复现的？ |
| 扫描预算与准入控制 | 一次请求能碰多少数据是可以事先约定的；超预算时**当场拒绝**比"慢慢扫完再报错"更安全 | 线上接口怎么防止一次请求把资源吃光？ |

## Stage 2 · 内存与 swap ⬜

**亲手场景**：本地缓存没有上限、RSS 每天涨 300MB → 你用 `jcmd` 定位到容器类实例数，改成有界并解释 OOM 链路。

| 考点 | 一句话原理 | 面试题 |
|------|-----------|--------|
| `free` 的 available | `free` 减掉不可回收部分；`buff/cache` 大部分是**可回收**的页缓存，所以 `available` 才是可用内存 | `free` 里 cached 很大是内存不够吗？ |
| 页缓存 | 读写文件都先过页缓存；读缓存命中省的是设备 IO、写缓存让写系统调用立刻返回 | 为什么第一遍读文件比第二遍慢？ |
| swap in/out | 内存压力下内核把匿名页换到磁盘；`vmstat` 的 `si`/`so` 是换页速率，长期非零说明内存真的不够 | 什么时候 swap 会拖垮服务？ |
| OOM killer | 内核在无法回收时按 `oom_score` 杀进程；容器里表现为退出码 137 | 容器被 137 杀掉怎么定位原因？ |
| 有界缓存 | 声明了容量就必须自己负责驱逐；依赖 GC 或弱引用无法给出**确定**的内存上界 | 本地缓存怎么防止 OOM？ |
| 内存上界的可观测 | 存活条目数比堆字节数更适合做判据：后者受 JVM 版本、TLAB、压缩指针影响 | 你怎么验证一个修复真的降低了内存占用？ |
| 驱逐活性 | 光有上限不够：驱逐次数不涨说明缓存已经退化成"满了就不干活"；命中率会波动、驱逐次数不会 | 有界缓存怎么保证"还活着"？ |
| 容量耗尽的准入 | 满了以后只有两种确定结论：赶走谁、或拒掉这一次；"静默越界"是第三种，也是最坏的 | 缓存满了该拒绝还是该淘汰？ |

**复现命令**：`bash scripts/observe/02-memory-swap.sh`（`free -m` / `vmstat 1 10` / `grep -E 'pswp' /proc/vmstat`）

## Stage 3 · 磁盘 IO 与 fsync ⬜

**亲手场景**：10 万条导入把 `%util` 顶到 100% → 你用 `strace -c` 数出 fsync 次数与记录数一比一，改成分批。

| 考点 | 一句话原理 | 面试题 |
|------|-----------|--------|
| `iostat` 三件套 | `%util` 是设备忙的时间占比、`await` 是平均每请求等待+服务时长、`w/s` 是提交速率 | `%util` 100% 一定说明盘到瓶颈了吗？ |
| 顺序 vs 随机 | 机械盘差在寻道，SSD 差在写放大与 GC；同一份 IO 模式在两种盘上结论可能相反 | 为什么数据库的随机写比顺序写贵得多？ |
| 缓冲 IO vs 直接 IO | 缓冲 IO 走页缓存、可合并、但对掉电不保证；`O_DIRECT` 绕过缓存、把对齐与合并的责任交给应用 | 什么时候该用 O_DIRECT？ |
| `write()` 与落盘 | `write()` 只是把数据交给内核页缓存；只有 `fsync`/`fdatasync` 返回才代表数据真的落到介质上 | 事务提交后宕机，数据会丢吗？ |
| fsync 合并 | 一次 `fsync` 可以覆盖它之前的所有写；把 N 次落盘合并成 N/B 次，靠的就是这个语义 | 批量提交为什么能显著提高写入吞吐？ |
| 批量与丢失窗口 | 批次越大吞吐越高、单次异常能丢的数据越多；这是可调参数不是非黑即白的选择 | 怎么定一个写入批次的大小？ |
| 批次上界与下界 | 批次太小退化成逐条、太大变成一次全灌；两个方向都要有守卫，且守卫必须在**交出这一批之前**判定 | 批量提交的批次大小谁说了算？ |
| 流式与驻留峰值 | 有界 O(1) 内存的接口不能先读全量；"驻留了多少条"才是有上界的那个量，"总共读了多少条"不是 | 一个只读接口怎么做到内存不随输入增长？ |

**复现命令**：`bash scripts/observe/03-disk-io.sh`（`iostat -x 1` + `strace -c -f -e trace=write,fsync,fdatasync` + `/proc/self/io`）

## Stage 4 · 网络与上下文切换 ⬜

**亲手场景**：上游告警说我们每秒建连数千次 → 你用 `ss` 看出建连数等于请求数，改成复用并把 `TIME_WAIT` 讲清楚。

| 考点 | 一句话原理 | 面试题 |
|------|-----------|--------|
| TIME_WAIT | 主动关闭方等待 `2×MSL`，保证旧连接的迟到报文不会污染新连接；这段时间它仍占着四元组 | 服务器大量 TIME_WAIT 怎么办？ |
| 端口耗尽 | 临时端口范围有限，建连速率 × 2×MSL 超过可用端口数就会 `Cannot assign requested address` | 为什么压测客户端会报端口不够？ |
| keep-alive 与连接池 | 复用省掉握手/挥手与慢启动，代价是服务端要为闲置连接保留资源 | 长连接和短连接怎么选？ |
| 上下文切换 | 内核在 `vmstat` 的 `cs` 列统计；自愿切换来自阻塞等待，非自愿来自时间片耗尽 | 上下文切换高说明什么？ |
| 线程复用 | 线程创建本身便宜，但线程数决定调度与切换次数；池化把「每请求一个执行单元」变成固定规模 | 线程池大小怎么定？ |
| 可观测性 | 回环网络（`lo`）上 `tcpdump` 能看到完整握手；`ss -tan state time-wait` 直接数出等待态连接 | 怎么验证连接真的被复用了？ |
| 连接池容量 | 池容量是硬上限：并发超过它时应当排队或拒绝；"要多少给多少"等于没有池 | 连接池满了会怎样，你怎么设计这个行为？ |
| 响应归属 | 并发复用下必须能回答"这条响应属于哪次请求"；用一个"当前在飞请求"字段记归属，串行正确、并发必错 | 长连接上并发请求怎么防止串号？ |

**复现命令**：`bash scripts/observe/04-net-ctxswitch.sh`（`ss -s` + `ss -tan state time-wait | wc -l` + `tcpdump -i lo -nn` + `vmstat 1`）

## Stage 5 · 锁竞争与 futex ⬜

**亲手场景**：计数接口加到 8 核 QPS 只涨 15% → 你用两次 `jstack` 差集看到六个线程 `BLOCKED`，把耗时计算移出临界区。

| 考点 | 一句话原理 | 面试题 |
|------|-----------|--------|
| Monitor 与临界区 | `synchronized` 保护的是**共享状态**；把不需要保护的耗时计算放进去，等于人为制造串行 | 怎么减小锁的粒度？ |
| futex | 未竞争时在用户态完成、有竞争才进内核挂起；进内核就要上下文切换，比自旋贵得多 | 为什么说锁竞争会表现为上下文切换高？ |
| 自旋与自适应 | 短临界区适合自旋（省一次切换）、长临界区必须挂起（省 CPU）；JVM 会自适应 | 偏向锁/轻量级锁/重量级锁的升级过程？ |
| 锁的代价与核数 | 临界区占满整个操作时吞吐上限 = 单线程吞吐，加核只是让队伍变长 | 为什么加机器对某个接口没有用？ |
| 无锁累加 | CAS 保证原子性但不保证无等待；高竞争下无锁实现的失败重试也会退化 | `AtomicLong` 和 `LongAdder` 的区别？ |
| 观测锁 | `perf lock` 读锁事件给出等待次数/时长；`jstack` 的状态分布是最便宜的替代 | 线上怎么定位锁竞争？ |
| 临界区真相 | "能不能并行"与"串行化有没有被消除"是两个量：把耗时计算挪进另一把锁，第一个涨了、第二个照旧 | 换了锁的实现，你怎么证明临界区真的变小了？ |
| 口径对账 | 一次成功受理要写多处计数时，三处必须严格相等；"缩小临界区却忘了记账"是这类改动最常见的副作用 | 优化并发之后怎么确认没有丢计数？ |
| 有界等待 | 等待队列必须有上界：无界队列只是把"锁竞争"换成了"内存竞争"，而且被拒的那次不许有副作用 | 锁等待队列要不要限制长度？ |

> **与 database-bagu 的对照**：seckill-lab 的 Stage 3 讲的是**数据库行锁**（`FOR UPDATE`、间隙锁），
> 本 Stage 讲的是**用户态 futex 锁**。面试里「锁竞争怎么排查」这句话有时问的是前者、有时是后者，
> 两张地图放在一起看，你就能分清「锁在 MySQL 里还是在 JVM 里」。

**复现命令**：`bash scripts/observe/05-lock-futex.sh`（`perf lock record/report`；无权限时退化为 `jcmd Thread.print` 两次差集 + `vmstat 1` 的 `cs` 列）

## Stage 6 · 压力测试与容量评估 ⬜

**亲手场景**：容量评审会上发现报告的 P50 与 P99 只差 2.4ms → 你发现分位数是编出来的，改成从样本算并补上并发驱动。

| 考点 | 一句话原理 | 面试题 |
|------|-----------|--------|
| P50/P95/P99 语义 | 分位数是分布的分割点，必须来自样本；P99 与 P50 的比值反映尾部形状 | 为什么平均延迟没有意义？ |
| 分位数实现 | 排序取样最准但内存高；直方图省内存但有桶边界误差；报告要写明口径 | 你们的 P99 是怎么统计的？ |
| 并发与排队 | 并发度提高时延迟上升往往来自排队而不是代码变慢；要区分服务时间与等待时间 | 压测时并发数怎么选？ |
| 吞吐 vs 延迟 | 两个量纲不同的量，混在一张表的同一列会让人直接算错实例数 | 高吞吐低延迟能同时做到吗？ |
| 容量评估方法 | 单实例能力 × 目标流量 × 冗余度，且必须带假设与误差范围；绝对值不能跨机器搬运 | 给你一个 P99 数字，你能算出要几台机器吗？ |
| 可复现的压测 | 固定并发、固定输入、多轮取中位数、记录环境；不可复现的数字不能进任何结论 | 你的压测结果别人能复现吗？ |
| 报告出口守卫 | 每个字段必须对应一个明确定义的量：把 P99 印在吞吐那一列，读报告的人会直接算错实例数；量纲错栏应当在**出口处**被拦住 | 你怎么保证压测报告不误导人？ |
| 并发上限 | 压测并发度是声明出来的上界，超限应当拒绝并记录；"要多少给多少"会让报告看起来更强，但那不是真的 | 压测的并发度谁定、超了怎么办？ |

**复现命令**：`bash scripts/observe/06-capacity.sh`（串行与并发两轮压测 + 分位数口径对照；结果只作观察，不作判据）

- **eBPF / bpftrace**：内核态可编程追踪（`biolatency`、`runqlat`、`offcputime`）。本项目只到 `perf` 为止——eBPF 需要内核版本与 BTF 支持，装不上的机器占相当比例，会造成"文档里能跑、我机器上跑不了"。

### 6.1 判定面逐条论证

| 路径 | 为什么它是判据所依赖的 | 为什么学员不许改 |
|---|---|---|
| `./src/test/` | 六组 canonical 测试**与全部计数包装器**都在这里。本 Track 的判据 100% 是「计数器读数」，而计数器就是这里的 `CountingRegex` / `WorkCounter` / `BudgetRegistry` / `CacheRegistry` / `AdmissionRegistry` / `CountingChannel` / `StreamCursor` / `CountingSocketFactory` / `CountingThreadFactory` / `GuardedWorkConcurrency` / `SampleProjection` 夹具（后四个是 v1.1 新增，见下条） | 改一行就能让六个 stage 全绿（例如把 `CountingRegex.compileCalls()` 改成恒返回 1）。这是本 Track **最直接**的作弊通道，必须首条声明 |
| `./pom.xml` | 夹具规模与阈值由 Surefire 的 system property 注入（`-Dlab.rows=4000`、`-Dlab.batch.max=128`、`-Dlab.pool.capacity=4`、`-Dlab.queue.bound=4`、`-Dlab.concurrency.cap=…` 等）；`forkCount=1`/`reuseForks=true`/`parallel=none` 是「计数器在用例之间不串」的前提 | 改它可以把夹具规模改小（4000 行改成 4 行）、把上界放宽（批次上界从 128 改成 `Integer.MAX_VALUE`，于是 `FsyncPolicyGuard` 永不拒绝）、把测试组排除掉、把并行打开让计数互相污染 |
| `./scripts/` | `build.sh` 是准入门「骨架可构建」的入口；`digest-pin.sh` 生成摘要；`observe/*` 是 B 类手册的执行体 | 改 `build.sh` 可以伪造构建成功；改 `observe/*` 可以伪造 B 类证据（虽然 B 类不进硬门，但伪造证据会污染答辩材料） |

| `./docs/Linux性能八股地图.md` | `ticket.submission.bagu_map_ref` 的锚点来源（准入门有 `bagu_map_anchor` 硬门）；也是「过关后讲解」的内容归属 | 改标题会让锚点失配（门会响），但更坏的情况是**学员把地图当成答题区**去改表格内容——地图是讲解材料，不是实现 |

**v1.1 新增的四个判定面文件的归属论证**（这是本轮唯一动了判定面的地方，逐条说明为什么它们必须在判定面、而不是在学员改动面里）：

| 新增的判定面文件 | 它为什么属于判定面（而不是学员改动面） | 为什么它必须存在 |
|---|---|---|
| `fixture/BudgetRegistry.java` | 它记的是「拒绝了几次、按什么原因拒的」，而拒绝次数正是 Stage 1 边界判据的读数——读数放在学员手里等于把判据交出去 | Stage 1 的新边界路径（扫描预算耗尽被拒）需要一个**学员改不到**的计数器；学员自己那本 `SearchWorkLedger` 是业务口径，两者不一致时以本文件为准 |
| `fixture/AdmissionRegistry.java` | 同上：它按桶（缓存 / IO / 网络 / 锁）记「准入了几次、拒绝了几次」，三个 stage 的边界判据都读它 | 让「被拒」这件事在四个 stage 上**用同一套口径**度量，否则每条边界路径各写一套计数，互相之间不可比对 |
| `fixture/StreamCursor.java` | 它数的是**游标归属**（一个批次里有几条被物化、峰值是多少），这是 Stage 3 的判据读数；学员的 `RecordSource.stream()` 是**被观测的对象** | 「驻留峰值」必须由**游标的观察者**数，而不能由游标自己报——否则"把峰值报小一点"就是一条免费通道 |
| `fixture/SampleProjection.java` | 它实现「这个值是不是样本集合的成员」与「样本的有序投影」，是 Stage 6 分位数判据的**唯一**成员判定实现 | 若让学员的 `LatencyRecorder` 自己判断"我返回的是不是样本"，成员关系就成了自证；放在判定面才能让"编一组好看的数"必然被抓住 |

**这四个文件全部进 `protected_paths`**（落在 `./src/test/` 之下），并且**属于 `digest_pin.tests` 的覆盖范围**——
即「改一行让边界判据变绿」与「删掉一个文件」都会同时触发 tampering 与摘要失配。它们的 Javadoc 只写**读数语义**
（"本包装器记录被拒绝的次数，按原因分桶"），**不写**任何 stage 的实现方向。

### 6.2 必须 pin 的东西

- **文件摘要**：`compose` / `build` / `tests` / `sim` / `observe` 五个入口，由 `scripts/digest-pin.sh` 生成（配方照抄 seckill-lab：目录入口按文件名排序后逐个 `sha256sum` 再拼接哈希，保证「新增一个测试文件」也会让摘要变）。**`tests` 这一个入口已经覆盖 v1.1 新增的四个判定面文件**（`BudgetRegistry` / `AdmissionRegistry` / `StreamCursor` / `SampleProjection`），因为它们在 `./src/test/java/com/devteam/osperf/fixture/` 之下——这是刻意的：**判定面的新增不需要动 `digest_pin` 的键名**，只要重跑一次 `digest-pin.sh` 让 `tests` 的摘要值跟着变。
- **镜像摘要**：`eclipse-temurin:17-jdk`（app 的构建与运行基础）与 `curlimages/curl:8.8.0`（pinger）。**必须 pin digest 而不是 tag**——`:17-jdk` 这种 tag 会随补丁版漂，而 JVM 的小版本差异会直接改变 GC 行为（进而改变 B 类观察的读数），这是本 Track 比其他 Track 更在意镜像锁定的原因。
- **为什么 `observe` 也要 pin**：它是**真在学员机器上跑**的脚本（会执行 `perf`、`sysctl -a`、`strace`），属于供应链攻击面；同时它也是 B 类证据的产生者。
- **重算时机**：改完 `runtime` 指向的任何文件（含 `scripts/observe/` 下新增一个脚本）就要重跑一次 `digest-pin.sh`；`ticket.grader.correctness.canonical_test` 若同步改路径，还要 bump `ticket_version`。

### 6.3 requires 与「perf 的内核参数 / 权限门槛」写清

```yaml
manifest:
  requires:
    # ── A 类（canonical 判据）真正依赖的：只有这些缺了会让 Track 不成立 ──
    java: "17"                 # 骨架与 canonical 测试（Jakarta/EE 无关，纯 JDK）
    build: maven               # mvn -B -o -DskipTests compile；★ 需预热本地 ~/.m2（见下）
    python: "3.11"             # scripts/observe/* 的解析脚本（只用标准库）
    docker: "24"               # compose v2；用于 compose up、cgroup 配额演示

    # ── B 类（实验手册）才依赖的：缺失只降级价值，不影响任何判据 ──
    perf: "optional"           # ★ 很多发行版把 perf 拆成 linux-tools-$(uname -r)，默认不装
    kernel.perf_event_paranoid: "<=1"      # ★ 非 root 采栈的硬门槛；=2 时连 kernel 事件都读不到
    kernel.kptr_restrict: "0"              # 火焰图要符号化内核栈；=1/2 时内核帧显示为地址
    kernel.sched_schedstats: "1"           # 读 /proc/schedstat 与调度延迟（可选）
    kernel.swap_enabled: "true"            # Stage 2 的 swap 观察项；没开则该项判「不适用」
    kernel.cgroup_version: "v1 或 v2"      # Stage 2 的 OOM 演示路径不同，preflight 会打印实际版本
    kernel.dmesg_readable: "true"          # Stage 2 读 OOM 记录；容器里通常需要 --privileged 或 host dmesg
    iostat: "optional"         # sysstat 包；Stage 3 观察项
    strace: "optional"         # Stage 3 数系统调用（有 /proc/self/io 时可退化为不必需）
    tcpdump: "optional"        # Stage 4 抓包
    fio: "optional"            # Stage 3 的 fsync 批次对照实验
```

**关于 `perf` 的门槛，规格里必须写清的六件事**（实施时由 `scripts/preflight.sh` 逐项打印，人话报错）：

1. **`kernel.perf_event_paranoid` 的默认值通常是 2**，此时非 root 用户**读不到任何内核事件**（`perf record` 报 `permission denied` 或采到的栈全是用户态地址）；内核栈采样需要 `<= 1`，`perf trace` 的 syscall 事件通常要 `<= 1` 或直接 root。
2. **临时放开**（重启失效）：`sudo sysctl -w kernel.perf_event_paranoid=1`；**持久化**写到 `/etc/sysctl.d/99-osperf-lab.conf`。规格要求 `preflight.sh` 把这件事**显式打印成建议命令**，而不是让学员去搜。
3. **`kptr_restrict`**：值为 1/2 时内核符号被隐藏，火焰图里内核帧会变成裸地址。要拿到可读的内核栈需要 `kptr_restrict=0`（或 root）。**这一条只影响可读性，不影响 A 类判据**。
4. **容器里基本不可用**：默认 `seccomp`/`CAP_PERFMON` 缺失，`perf` 在容器里通常直接报 `No permission to enable ... event`。因此 B 类手册**必须在宿主上跑**，而不是 `docker compose exec` 里跑——这一点要在手册第一行写死。
5. **`perf` 可能根本没装**：Debian/Ubuntu 要 `linux-tools-$(uname -r)` 或 `linux-perf`，RHEL 系要 `perf`。`preflight.sh` 检测 `command -v perf`，缺失时给出各发行版的安装命令，并**明确说「装不上不影响过关」**。
6. **WSL2 / 部分云 VM 上不可用**：WSL2 的内核没有开齐采样所需的配置，很多云 VM 允许 `perf stat` 但禁止 `perf record -g`。`preflight.sh` 用一次「采样 1 秒、检查输出里是否有非空栈」的**自检**来判定，而不是只看 `command -v perf`。自检失败时，手册自动切换到 `jstack` 差集 + `jcmd` 的替代路径——这条替代路径是**必做**的，不能只在文档里提一句。

**关于离线（D3 的硬要求，本 Track 的头号开工前提）**：

- `scripts/build.sh` 与 `scripts/test-stage.sh` 都必须带 `-o`（offline）。依赖（JUnit 5、Surefire、Compiler、Resources 插件）必须在**开发机**上预热一次后，把 `~/.m2/repository` 的镜像层打进 app 镜像或随骨架仓分发。
- 因此 `track.yaml` 的 `requires.build: maven` 有一条隐含子要求，规格里明写：**发行版必须带一份预热好的本地仓库**（`docker/app.Dockerfile` 里把 `m2` 作为构建期 `COPY` 进来，或由 Track 提供一个 `scripts/warm-m2.sh` 供首次联网环境执行一次）。这是「离线可复现」这个硬约束在本 Track 上最容易被忽略、也最容易让整条 Track 作废的地方，故列进 §7 风险表首行。
- 六个 canonical 测试**全部不开网络**：`UpstreamClient` 的测试用进程内回环 `ServerSocket`，不解析域名、不连外网。

### 6.4 供应链注意

- **本 Track 会在学员机器上执行的东西**：`mvn`（构建与测试）、`java`（骨架自身）、`bash scripts/*`（`build/test-stage/digest-pin`）、`bash scripts/observe/*`（`perf`、`sysctl -a`、`ss`、`strace`、`iostat`、`tcpdump`）、`docker compose`（两个容器）。**没有 eBPF、没有内核模块、没有 `insmod`、没有 `sysctl -w` 的自动写入**——所有会改变宿主状态的命令（`sysctl -w`、`docker run --memory`）都由**学员手工执行**，脚本只打印不执行。这条纪律写进 `docs/架构与约定.md`。
- **第三方二进制**：只有两个镜像（temurin JDK / curl），都 pin digest。JVM 里的第三方库只有 JUnit 5 与 Surefire（都在本地 m2 里）。
- **引入的风险与它的缓解**：`scripts/observe/*` 会读 `/proc`、`/sys` 与 `dmesg`，这些是**只读**的；`perf` 本身需要 `perf_event_paranoid` 放宽——这是 Track 要求学员**主动**降低一层系统防护，必须在 `requires` 里声明、在 `preflight.sh` 里明示后果，并在手册里建议「在专用 VM 或容器宿主上做，做完可以调回去（`sysctl -w kernel.perf_event_paranoid=2`）」。这是本 Track 相对 seckill-lab（只起两个容器）**更高的信任成本**，应在 `trust_level` 上如实反映。

### 6.5 trust_level 建议

**建议 `self`**，理由与 seckill-lab 一致：本仓由部署方自己维护、自托管运行。但本 Track 有一条 seckill-lab 没有的成本——它**要求放宽一条内核安全开关**（`perf_event_paranoid`）。

因此规格给出更强的要求（若将来要升 `verified`）：

- `contribute.review.signed_by` 至少一位维护者对 `scripts/observe/` **逐脚本人审**（它们能读宿主的 `/proc`、`/sys`、`dmesg`）；
- `runtime.digest_pin` 覆盖 `observe` **目录**摘要（新增一个脚本就让摘要变，防止「merge 之后偷偷多跑一条命令」）；
- 在 catalog 的披露文案里**点名**「本 Track 会建议你临时放宽 `kernel.perf_event_paranoid`，并读取 `/proc` 与 `dmesg`」，让学员在拉取前就知道这件事。

**建议的实施顺序**（每一步都以「跑通一条最小的端到端链」为验收，而不是「写完所有文件」）：

1. **先做 Stage 5（锁竞争）**。理由：它的判据最硬（一个并发度计数）、夹具最轻（不需要大输入、不需要文件、不需要网络），而且是唯一一个能验证「计数器包装器 + 判定面 + 分层约定」这套技术前提是否成立的最小样本。它红了、绿了、`-sol` 也绿了，才说明本 Track 的判据方法论站得住。
2. **再做 Stage 1（CPU）**，验证「大夹具 + 计数上界」这条模式（它是 Stage 2/3/4 的模板）。
3. **然后 Stage 3（IO）**，验证「真委托包装器 + 两个方向的上界（下界防逐条、上界防全灌）」这条更细的模式。
4. **接着 Stage 2（内存）与 Stage 4（网络）**，它们复用 1 与 3 的模式，边际成本低。
5. **最后 Stage 6（容量）**，它的判据独立（纯结构断言），但要等前五个 stage 的端点都稳定后再做，否则并发驱动会反复返工。
6. **最后才做 B 类手册与 `preflight.sh`**——不是因为它不重要（它是本 Track 的产品价值所在），而是因为手册要拿**真实修好的骨架**跑一遍才能写准「看到什么算正常」。所有会被 `observe/*` 依赖的度量口径，此时都已经由 A 类判据钉死了。

> **v1.1 对实施顺序的两处补充**（不改变上面六步的次序）：
> ① 每做一级，**先把这个 stage 的 `*Guard` 与账本的单线程路径跑绿**（`-Dgroups=smoke` + 本级基线），
> 再去写那三条红判据——顺序反了很容易把"守卫没写完"误当成"边界判据已就位"（`_SCALE.md` §1.1 第 1 条）。
> ② 每一级的"边界/拒绝"用例要**先证明它在骨架上真的红**（拒绝计数为 0 或超限读数越界），
> 再证明它在 `-sol` 上绿；这一步是本轮最容易出废判据的地方——一个恒真的守卫会让用例"看起来过了"。

# 骨架落地清单（os-perf-lab / `os-perf-bagu`）

> 按顺序做；每一步做完都回来打勾。**判据形状没验掉之前不要写业务代码。**
> 依据：`docs/设计规格.md` 的 §1（判据可行性）、§2（骨架仓设计）、§3（Stage 与分支链）、
> §7（实施顺序）、§8（准入门自查清单）；规模下限见题库侧 `_SCALE.md`。

## 阶段 0 · 先验判据形状（不是先写功能）

- [ ] 按规格 §7 的「建议的实施顺序」挑出**判据最硬的那个 stage**（通常是根节点）
- [ ] 只做它的骨架 + canonical 测试 + `-sol` 参考解，把它在真机上跑成"骨架稳红 / 参考解稳绿"
- [ ] 骨架红必须**红在业务缺陷**上：不是编译错、不是零用例、不是装配失败
- [ ] 骨架必须**单线程正确**：环境体检（冒烟）与单线程基线全绿
      （扩面时最容易踩：把"顺序错/忘了回滚"这类**单线程可见**的缺陷塞进来——见 `_SCALE.md` §1.1）
- [ ] 连跑 20 次存档：骨架 20/20 红、`-sol` 20/20 绿

## 阶段 1 · 仓库基本骨架

- [ ] `track.yaml`：`manifest`（requires / skeleton_repo / bagu_map / stages）与
      `runtime`（各可执行入口 + `protected_paths` + `digest_pin`）
- [ ] `runtime.protected_paths` 每条都**真能匹配到**骨架里的东西（写错一个字母就是静默漏洞）
- [ ] `runtime` 里每个**已声明**的入口都有 `digest_pin`（未声明的入口不需要 pin）
- [ ] `scripts/digest-pin.sh` 跑通，pin 是**实测值**（不要 `sha256:PENDING` 占位——准入门只校验前缀，
      占位也能过门，所以更要自己盯住）
- [ ] `scripts/build.sh` 就是准入门"骨架可构建"的调用点
- [ ] `docs/架构与约定.md`：分层、并发/事务语义的落点、判据约定、判定面与 pin 纪律
- [ ] `docs/` 里的八股地图（`bagu_map`）标题**一次定稳**，锚点按平台 `_CONTRACT.md` §3.1 逐个演算

## 阶段 2 · 每个 stage 的工单与分支

- [ ] `stages/<stage-目录>/ticket.yaml` 八个 concern 写全；`scope.files_to_change` 的路径**真实存在**
- [ ] `submission.bagu_map_ref` 的锚点能在 `bagu_map` 里解析
- [ ] 题面 / concepts / hints **无解法行**（给方向可以，给答案不行），且不复述判据与提交要求
- [ ] `identity.ticket_version` 起 1；之后改题面或判据就 bump
- [ ] 分支链：`stage-NN-<slug>` = 上一阶段 + **本阶段测试**（只加不删）；`-sol` 从**同阶段 base** 切出
- [ ] 共享的判定面目录（如 `harness/`、`sim/`）在**第一个 stage 分支上就完整存在**
- [ ] `manifest.stages` 覆盖所有已发现的 `stages/*/ticket.yaml`

## 阶段 3 · 规模与收口

- [ ] 每个 stage 达到 `_SCALE.md` 下限：改动面 **≥3 文件**（三类角色各至少一个，
      且**点名**是哪三个）· canonical **≥5 条**（红 ≥2 条且分属不同不变量、单线程基线 ≥2 条、
      边界/拒绝路径 ≥1 条）· 考点族 ≥2
- [ ] 参考解 diff 与改动面规模相称（并发/算法类 Track 的 diff 天然小，规模靠文件数与不变量数撑）
- [ ] `TASKS/` 叙述视图与 `ticket.yaml` **不漂移**（事实只存一份，冲突以 yaml 为准）
- [ ] 证据归档：`TASKS/evidence-stage-NN/`（红绿日志 + 稳定性日志 + REPORT.md，
      含**没能验证的部分**）
- [ ] 平台准入门自查：逐条对照题库侧 `_CONTRACT.md` §4 与规格 §8
